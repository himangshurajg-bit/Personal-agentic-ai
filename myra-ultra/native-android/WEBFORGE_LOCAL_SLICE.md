# WebForge local project slice

This slice ports the source-backed local project workflow from `MYRA_ULTRA_APP/website_builder/project/project_manager.py`: create a project folder with `css`, `js`, and `assets`; write an `index.html`; list projects; and update project files. Android stores projects under the app-private `filesDir/webforge-projects` directory. The screen edits `index.html`, `css/style.css`, and `js/script.js`, then saves them locally.

The preview combines those three files in an Android WebView. It has no JavaScript bridge, file/content access, DOM storage, database, popups, forms, frames, external navigation, or network-resource access. A restrictive Content Security Policy blocks network connections and external resources. JavaScript runs only inside the preview so a project can use its local script; this does not make untrusted site code safe for publication. No deployment, sharing, or GitHub/Vercel connection is implemented. A separate generation path sends only the user-entered prompt to the selected Gemini model after a disclosure/confirmation; existing project files are never included. Gemini output is size-bounded and shown in editable HTML/CSS/JavaScript review fields, and is not written until the user taps Save generated project, which creates a new local project rather than overwriting an existing one. Model output is untrusted; the offline preview blocks network requests and external navigation, has no native bridge, and does not publish code. A user-triggered ZIP export writes visible project files to a location selected in Android’s document picker; it does not upload or deploy them.

This is a local WebForge authoring slice with a narrow prompt→generate→review→save Website Studio path, not a complete port of Website Studio or the MYRA Coder agent. In addition to the three preview files, it now lists, opens, creates and edits arbitrary nested project-relative text files, following the upstream `ProjectManager.list_all_files` / `write_files` behavior in `MYRA_ULTRA_APP/website_builder/project/project_manager.py`. File editing rejects absolute paths, traversal, hidden paths, metadata edits and symbolic links; it caps each file at 200,000 characters and each project at 500 visible files. Project data remains in app-private storage.
A narrow MYRA Coder context-preparation slice follows `MYRA_ULTRA_APP/myra_coder/src/context/attachments.ts`: a task can reference visible project files with `@path`, and the app locally previews their numbered contents before the original task. It deduplicates references, warns on unresolved or unsafe paths, and caps the preview at five files, 120,000 combined file characters, and a 4,000-character task. The user can explicitly send the exact task and referenced excerpts shown in the preview to Google Gemini, using the selected model and encrypted saved key; MYRA discloses the transfer and requires confirmation first. The bounded text answer is review-only: no model tools, shell, MCP, subagents, or automatic edits are enabled. A separate local patch path follows upstream `str_replace`/`write_file` intent without giving the model filesystem access: the user selects one existing visible file, pastes a full proposed replacement, reviews its complete before/after text, and confirms. The model-assisted path lets the user select one existing visible file and task, inspect the exact single-file payload and SHA-256 source fingerprint, then explicitly confirm sending only that file and task to Google Gemini using the selected model and encrypted key. Gemini must return one bounded JSON complete-file replacement (20,000 characters maximum); malformed, fenced, empty, truncated, oversized or stale-source results are rejected. The UI then shows the full before/after and source SHA-256 and requires a second explicit confirmation for the local write. Both paths cap versions at 20,000 characters, recheck exact on-disk contents and SHA-256 before writing, keep one hidden app-managed undo record per project, and refuse undo if the file changed afterward. The user must undo the last patch before applying another; incomplete or stale operations fail closed. Model output is never run and never writes automatically. Upstream Coder’s provider integrations, planning/ask modes, and tool-executing agent loop remain unported.

The upstream Coder `/init` behavior in `MYRA_ULTRA_APP/myra_coder/src/init.ts` also has a narrow local counterpart: the user can create a `MYRA_CODER.md` starter from visible project filenames, folder layout, detected file extensions, and known package-lock filenames. It does not read source contents, infer runnable commands, run shell commands, overwrite an existing guide, or send data to a model; users can review/edit the guide with the existing project-file editor. The upstream generator/deploy pipeline in `website_builder/webforge_manager.py` also creates README files, previews projects, and may push to GitHub/Vercel. Those network and deployment flows are deliberately not enabled here. This slice does not execute Python agents or reproduce Coder's provider workflows; arbitrary project files are editable but are not yet resolved as assets in the offline preview. ZIP export follows the upstream Studio export concept but excludes hidden paths, `node_modules`, and `.myra-coder`; it rejects more than 500 files, files over 10 MiB, or projects over 20 MiB. It writes only after preflighting file sizes and checks sizes again while streaming. Tests cover recursive listing, nested read/write, path/symlink rejection, size/file-count bounds, bounded ZIP contents, project persistence, static review findings, and the offline preview policy. Build/test success does not verify WebView runtime enforcement or device behavior.

Generation uses the existing encrypted Gemini key and selected model through the existing HTTPS API endpoint; the key is read only at the network boundary and is not displayed or logged. The prompt limit is 4,000 characters; model response and each output file are bounded. The generator asks for a self-contained page and rejects missing HTML/CSS or over-limit files. The UI clearly warns that the prompt goes to Google before the user starts generation. The user can edit all returned files and the new project name before Save. These code/build tests do not verify live Gemini access, runtime WebView enforcement, or Android 16/Redmi behavior.


## MYRA Coder TODO panel

The project screen has an ordered task list modeled on upstream `myra_coder/src/tools/update_todos.ts`: each entry carries a stable ID, short content, and one of `pending`, `in_progress`, `completed`, or `failed`; a full ordered list replaces the previous one. A user can add tasks, change status, and remove entries (the panel retains at least one item). Marking one task in progress returns any previously in-progress task to pending, matching the upstream instruction to keep at most one active. Lists are stored only in each project’s hidden `.myra-coder/todos-v1.tsv` file using bounded encoded text; they are not added to visible project exports and are not sent to Gemini. The model cannot alter this list: edits are explicit UI actions. This is a local task panel, not the upstream agent-side tool execution/runtime.


## MYRA Coder `set_mode` gap

The upstream contract in `MYRA_ULTRA_APP/myra_coder/src/tools/set_mode.ts` requires a target `mode` (`agent`, `plan`, or `ask`) and a short `reason`, then delegates to `ctx.requestModeSwitch`. In manual mode that callback asks the user to approve before changing the session; in auto mode it changes mode and merely informs them. The change is operational, not just a label: `modes.ts` changes the prompt and tool registry. `plan` and `ask` are read-only; `agent` adds `write_file`, `str_replace`, `run_bash`, process controls, memory tools, subagents, and dynamic agent tools.

The Android Coder is currently a sequence of bounded, user-started Gemini requests and local review screens, not a persistent agent session. It has no mode-aware prompt/turn loop or mode-scoped tool registry. Its app-wide Gemini chat tools are independently allowlisted and latest-message/approval gated; they are not the Coder toolset. Adding an `agent` selection would therefore falsely imply shell, multi-tool orchestration, and autonomous work that this Android port does not implement. A `plan`/`ask` toggle would only decorate one-shot prompts and would not reproduce upstream switching or tool gating. No speculative mode selector or `set_mode` behavior was added; plan/ask/agent modes remain unported until a safe, explicit mode-aware Coder session and tool boundary exist.
